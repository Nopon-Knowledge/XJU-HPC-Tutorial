# 高算平台 JH UniScheduler 作业调度系统命令手册

本文介绍西京超算平台普通用户最常用的 JH UniScheduler 命令，并为每类命令提供可复制的示例。命令已于 2026-07-19 在登录节点 `mu01`、JH UniScheduler 6.3 上做过只读核验。

> 登录节点只用于编辑、下载、环境配置和提交作业。训练、编译、大规模数据处理以及 GPU 检测必须通过 `jsub` 提交到计算节点。
>
> 队列、节点、GPU 型号和账号权限会变化。每次提交前都应重新运行 `jqueues -u "$USER"` 和 `jhosts`。

## 1. 命令总览

| 命令 | 用途 | 最常用示例 |
| --- | --- | --- |
| `jqueues` | 查看队列及本人可用队列 | `jqueues -u "$USER"` |
| `jhosts` | 查看计算节点和资源状态 | `jhosts` |
| `jsub` | 提交 CPU 或 GPU 作业 | `jsub -q normal -o hello.out hostname` |
| `jjobs` | 查看作业状态和详情 | `jjobs -l JOBID` |
| `jctrl peek` | 查看未完成作业输出 | `jctrl peek JOBID` |
| `jctrl stop` | 暂停作业 | `jctrl stop JOBID` |
| `jctrl resume` | 恢复暂停作业 | `jctrl resume JOBID` |
| `jctrl kill` | 终止作业 | `jctrl kill JOBID` |
| `jctrl top` | 将本人等待作业移到队列前部 | `jctrl top JOBID` |
| `jctrl bot` | 将本人等待作业移到队列后部 | `jctrl bot JOBID` |
| `jctrl requeue` | 终止并重新排队 | `jctrl requeue JOBID` |

`JOBID` 是提交成功后调度器返回的作业号。示例中的 `JOBID`、节点名、队列名和路径都必须替换为真实值。

## 2. 查看命令帮助

### `jsub --help`

查看当前版本的提交参数：

```bash
jsub -V
jsub --help || true
```

该版本即使成功打印帮助，也可能返回退出码 1，因此在 Shell 脚本中查看帮助时可加 `|| true`。

### `jctrl --help`

查看作业控制子命令：

```bash
jctrl --help || true
jctrl peek --help || true
jctrl kill --help || true
```

平台升级后，应优先以当前帮助和管理员通知为准。

## 3. `jqueues`：查看队列

### 查看全部可见队列

```bash
jqueues
```

这个命令用于查看队列名称、状态和资源概况。

### 查看本人匹配的队列

```bash
jqueues -u "$USER"
```

实测账号可见的队列包括 `normal`、`docker_image`、`ai_excl`、`ai_share`、`ai_gmem`、`cpu` 和 `gpu`，但其他账号可能不同。

需要同时检查：

- 队列是否出现在本人查询结果中。
- `STATUS` 是否为 `Open:Active`。
- 队列是否提供程序需要的 CPU、内存或 GPU。

`jqueues -u "$USER"` 也可能列出 `Closed:Active` 的匹配队列。出现在结果中不等于当前一定可以提交。

## 4. `jhosts`：查看节点资源

### 查看全部节点

```bash
jhosts
```

用于查看节点名称、状态、CPU、内存和 GPU 等资源。提交 GPU 作业前，应先确认所需 GPU 类型当前存在。

<img src="../images/jhosts.png" width="85%" alt="jhosts 输出示例">

### 查看指定节点详情

```bash
NODE_NAME=gpu02
jhosts -l "$NODE_NAME"
```

`-l` 会显示指定节点的详细资源与属性。节点名必须来自当前 `jhosts` 输出，不要长期照抄示例中的 `gpu02`。

平台实测可见 RTX 3090、A800 80GB、A40 和 RTX 4090 等 GPU，但节点状态和资源会动态变化。

## 5. `jsub`：提交作业

基本格式：

```text
jsub [资源参数] COMMAND [ARGUMENTS...]
```

### 作业提交格式

常用参数展开后的格式如下：

```text
jsub -n <CPU核数> -m <指定节点或节点组> -W <时:分> \
  -gpgpu <GPU数量和GPU类型> -q <队列名> -J <作业名> \
  -o <输出文件名> -e <错误输出文件名> \
  -cwd <作业执行路径> ./commandline
```

`<...>` 中的内容是提交时需要替换的关键值，不要把尖括号原样输入终端。`./commandline` 表示实际运行的命令，例如当前目录下的可执行程序 `./train`，也可以替换成 Python 解释器和脚本路径。

**上面列出了常用参数，不表示每一项都必须填写。** 未指定的选项由系统调用默认配置；具体必填情况见下方参数表。若目标队列有额外要求，则按该队列要求填写。

### 示例 1：最简单的作业，打印计算节点名称

在登录节点终端执行：

```bash
jsub -q normal -o hello.out hostname
```

这条命令提交一个运行 `hostname` 的作业，用来熟悉提交过程，不需要准备 Python 环境或脚本。

- `jsub`：把后面的程序交给调度器，在获得资源后由计算节点执行。
- `-q normal`：提交到 `normal` 队列。该队列必须对你的账号开放，否则换成自己可用的 CPU 队列。
- `-o hello.out`：把作业的标准输出写入提交目录下的 `hello.out`。
- `hostname`：实际运行的程序，输出执行该作业的计算节点名称。

这条命令没有指定 CPU 核数、内存和时限，使用平台或队列的默认配置。提交成功只表示作业进入调度系统；用 `jjobs` 查看状态，完成后用 `cat hello.out` 查看节点名称。

### 示例 2：提交一个 CPU Python 作业

假设项目位于 `$HOME/python_project/my_project`，CPU 程序为 `main.py`，项目环境中的 Python 位于 `$HOME/venvs/my_project/bin/python`。先进入项目目录：

```bash
cd "$HOME/python_project/my_project"
```

`cd` 将当前目录切换到项目目录。后面使用相对路径的脚本和日志都以该目录为基础。`$HOME` 是你的用户主目录，`my_project` 要替换为真实目录名。

然后提交：

```bash
jsub -q normal -n 2 -J cpu-test -o "cpu.%J.out" -e "cpu.%J.err" "$HOME/venvs/my_project/bin/python" main.py
```

- `-q normal`：选择可用的 CPU 队列。
- `-n 2`：申请 2 个 CPU 核。程序是否会同时使用两个核，还取决于它自身的线程或进程设置。
- `-J cpu-test`：给作业命名，方便在 `jjobs` 的结果中辨认。
- `-o "cpu.%J.out"`：保存标准输出，例如 Python 的 `print()` 内容。
- `-e "cpu.%J.err"`：保存标准错误输出，例如未捕获异常的报错信息。
- `"$HOME/venvs/my_project/bin/python"`：使用项目环境的 Python，提交前需要确认该环境已安装项目依赖。
- `main.py`：要执行的脚本，位于刚才进入的项目目录中。

假设作业号是 `18433`，两份日志分别是项目目录下的 `cpu.18433.out` 和 `cpu.18433.err`。这条命令没有申请 GPU，适用于不需要 GPU 的程序。

### 示例 3：最简单的单 GPU 训练作业

在项目目录下执行，假设训练入口是 `train.py`：

```bash
jsub -q gpu -gpgpu 1 "$HOME/venvs/my_project/bin/python" train.py
```

- `-q gpu`：明确提交到 `gpu` 队列。如果你的可用 GPU 队列叫其他名字，就替换 `gpu`。
- `-gpgpu 1`：向调度器申请 1 张 GPU，不限定 GPU 类型。只写 `-q gpu` 不能代替 GPU 资源申请。
- `"$HOME/venvs/my_project/bin/python"`：指定已经安装训练依赖的 Python 环境。
- `train.py`：在计算节点上运行项目目录中的训练脚本。

这是单 GPU 作业的简写。CPU、内存和运行时限使用平台或队列默认配置，适用于默认值满足程序需求的情况。这条命令没有指定日志文件，输出按平台默认方式处理；实际训练建议使用下一个示例保存日志。申请 GPU 负责分配资源，训练代码本身也需要配置为使用 GPU。

### 示例 4：指定 CPU、内存、时限并保存训练日志

仍在项目目录下执行：

```bash
jsub -q gpu -gpgpu 1 -n 4 -M 16384 -W 02:30 -J my-train \
  -o "train.%J.out" -e "train.%J.err" \
  "$HOME/venvs/my_project/bin/python" train.py --epochs 10
```

这条命令申请 **1 张 GPU、4 个 CPU 核和 16384 MB 主机内存**，最长运行 **2 小时 30 分钟**。

- `-q gpu`：提交到指定的 GPU 队列。
- `-gpgpu 1`：申请 1 张 GPU。
- `-n 4`：申请 4 个 CPU 核，可供程序的数据读取、预处理等工作使用。
- `-M 16384`：指定 16384 MB 主机内存。这不是 GPU 显存，不能用它增加显卡的显存容量。
- `-W 02:30`：设置作业最长运行时间，格式是“时:分”。程序可以提前结束；该参数不表示要等待 2 小时 30 分钟才开始运行。
- `-J my-train`：设置作业名为 `my-train`。
- `-o "train.%J.out"`、`-e "train.%J.err"`：分别保存标准输出和标准错误，用作业号区分多次提交的日志。
- `"$HOME/venvs/my_project/bin/python" train.py`：使用项目环境运行训练脚本。
- `--epochs 10`：传给 `train.py` 的程序参数，假设该脚本支持用它设置训练轮数。它不是 `jsub` 参数；如果你的脚本不支持，就删除或替换为脚本实际支持的参数。

作业号若为 `18433`，输出文件是 `train.18433.out`，错误文件是 `train.18433.err`，均位于项目目录。资源数值和时限只是示例，应根据程序需要和队列限制调整。

命令末尾的 `\` 表示下一行仍属于同一条命令，后面不要加空格；也可以把整条命令写在一行。`jsub` 的资源和日志参数放在 Python 命令前面，脚本参数放在 `train.py` 后面。

### 示例 5：指定节点和作业执行目录

假设已经确认 `gpu02` 是目标队列中对你可用的节点，项目目录已存在。可以在登录节点的其他目录提交：

```bash
jsub -q gpu -m gpu02 -gpgpu 1 -n 4 -W 01:00 -J node-train \
  -cwd "$HOME/python_project/my_project" \
  -o "$HOME/python_project/my_project/node.%J.out" \
  -e "$HOME/python_project/my_project/node.%J.err" \
  "$HOME/venvs/my_project/bin/python" train.py
```

- `-q gpu`：选择队列，目标节点必须能通过该队列使用。
- `-m gpu02`：指定作业在 `gpu02` 节点上执行。`gpu02` 是示例，需按当前 `jhosts` 和队列配置替换；也可以填平台已有的节点组名称。
- `-gpgpu 1`：在所选节点上申请 1 张 GPU。指定 GPU 节点后，仍需申请 GPU 资源。
- `-n 4`：申请 4 个 CPU 核。
- `-W 01:00`：最长运行 1 小时。
- `-J node-train`：设置作业名。
- `-cwd "$HOME/python_project/my_project"`：将计算节点上的工作目录设为项目目录，因此 `train.py` 会从该目录中查找。
- `-o`、`-e` 后面的绝对路径：明确把两份日志放到项目目录中，不依赖你在登录节点的哪个目录提交。
- 最后的 Python 路径和 `train.py`：指定训练环境与程序入口，二者都必须在计算节点可访问。

这个例子适合确实需要特定节点的情况。指定节点后，可调度范围会缩小，目标节点资源不足时可能需要继续排队。没有这个需求时，删除 `-m gpu02`，让调度器选择符合条件的节点。

### 示例 6：指定 GPU 类型

在项目目录执行。下面以本手册此前核验过的 A800 80GB 类型字符串为例，提交前仍需确认平台当前提供该类型：

```bash
jsub -q gpu -gpgpu "1 type=NVIDIAA80080GBPCIe" -n 4 -J a800-train \
  -o "a800.%J.out" -e "a800.%J.err" \
  "$HOME/venvs/my_project/bin/python" train.py
```

- `-q gpu`：选择能够提供目标 GPU 类型的队列。
- `-gpgpu "1 type=NVIDIAA80080GBPCIe"`：申请 1 张指定类型的 GPU。`1` 是数量，`type=...` 是类型条件；整个值包含空格，所以用引号括起来。
- `NVIDIAA80080GBPCIe`：调度器识别的类型字符串，不是任意填写的商品简称。需要换型号时，应使用平台当前配置中的准确字符串。
- `-n 4`：同时申请 4 个 CPU 核。
- `-J a800-train`：设置作业名，便于区分其他训练作业。
- `-o "a800.%J.out"`、`-e "a800.%J.err"`：将标准输出和标准错误分别写入项目目录下带作业号的日志文件。
- 最后的 Python 路径和 `train.py`：使用项目环境执行训练脚本。

这条命令限制 GPU 类型，但没有指定节点，调度器可以在符合条件的节点中选择。没有该类型的空闲资源时，其他型号即使空闲，也不满足这项申请。若不限制型号，把 GPU 参数改为 `-gpgpu 1` 即可。

### 哪些必填，哪些可选？

这里讨论的是上面这种直接在命令行提交程序的方式。需要区分命令本身的必需内容、指定 GPU 作业时需要显式填写的内容，以及可按需添加的选项。

| 参数或内容 | 是否必填 | 作用与示例 | 省略时的处理或注意事项 |
| --- | --- | --- | --- |
| `COMMAND [ARGUMENTS...]` | **必填：要运行的程序** | `hostname` 或 `"$HOME/venvs/my_project/bin/python" train.py` | 必须告诉调度器运行什么；程序参数是否必填由程序本身决定 |
| `-q QUEUE` | **指定队列时必填；本教程建议始终填写** | `-q gpu` 指定作业使用的队列 | 队列由管理员分配使用；省略时依赖系统默认队列，不能保证进入目标 GPU 队列 |
| `-gpgpu SPEC` | **本教程的 GPU 作业需填写；CPU 作业不用填** | 申请 GPU 数量和类型；`-gpgpu 1` 表示申请 1 张 GPU，不限定类型 | 类型可按需指定；不应依赖队列名称自动申请 GPU，数量与类型须符合队列策略 |
| `-n CORES` | 可选；训练时建议填写 | `-n 4` 申请作业所需的 4 个 CPU 核 | 不能超过队列资源限制；省略时使用默认配置，不是 GPU 张数或节点数 |
| `-m HOSTS` | 可选；需要指定节点时填写 | `-m gpu02` 指定在某个节点或节点组上执行 | 省略时由调度器选择符合资源要求的节点；名称应来自当前平台配置 |
| `-M MB` | 可选；训练时建议填写 | `-M 16384` 指定 16384 MB 主机内存 | 使用平台或队列默认配置；省略不表示内存无限制 |
| `-J NAME` | 可选 | `-J my-train` 设置便于识别的作业名 | 仍会获得作业号，可用作业号查询和管理 |
| `-o FILE` | 可选；建议填写 | `-o "output.%J"` 指定调度系统收集的作业输出文件，包含程序的标准输出 | `%J` 代表作业号；省略时输出按平台默认方式处理 |
| `-e FILE` | 可选；建议填写 | `-e "error.%J"` 指定可执行程序运行时的标准错误输出文件 | 省略时不会生成单独指定的错误日志，错误输出按平台默认方式处理 |
| `-cwd DIR` | 可选 | `-cwd "$HOME/python_project/my_project"` 指定作业在派发节点上的执行路径 | 默认使用提交目录；路径须在计算节点可访问，并满足目录权限要求 |
| `-W LIMIT` | 可选；队列有要求时填写 | 指定最长运行时间，格式为 `时:分`；`-W 02:30` 表示 2 小时 30 分钟 | 省略时使用默认配置，仍受队列时限约束；填写值不能超过队列允许的上限 |

**可选指命令语法允许省略，不代表所有队列都接受省略。** 管理员可能要求显式填写 CPU、内存、时限，或者限制每张 GPU 对应的 CPU 核数。上面的简写适用于队列默认配置满足要求的情况；提交被拒绝时，根据提示补充参数。可以用 `jqueues -l gpu` 查看目标队列的详细配置，将 `gpu` 换成实际队列名。

### 队列、GPU 类型和路径怎么填？

队列由管理员分配。提交前用下面的命令列出自己有权限使用的队列：

```bash
jqueues -u "$USER"
```

也可以写成 `jqueues -u 你的账户名`，用真实账户名替换中文。作业会进入 `-q` 指定的队列，资源不足时排队，满足资源和调度条件后派发执行。

只要求 GPU 数量时写 `-gpgpu 1`；还需要限定 GPU 类型时，填写数量和平台识别的类型字符串，并把整个值放在引号内：

```text
-gpgpu "<GPU数量> type=<GPU类型字符串>"
```

GPU 类型字符串应按平台当前帮助和资源配置填写，不能直接猜测商品名称。`-m` 指定的是节点或节点组，`-gpgpu` 指定的是 GPU 资源，两者用途不同。没有指定节点的需求时，可以省略 `-m`，让调度器选择节点。

`-o output.%J` 中的 `%J` 会替换成实际作业号。例如作业号是 `18433`，会生成 `output.18433`。本节示例先进入项目目录提交，因此输出文件也位于该目录；需要明确日志位置时，可以直接填写绝对路径。

`-cwd` 指定的是作业在计算节点上的执行目录，默认使用提交目录。按平台说明，应确保该路径每一层目录都具有所需的读、写、执行权限；尤其要保证能进入各级目录、读取项目文件，并在需要保存日志和结果的目录中写入文件。

日志直接写在项目目录时不需要额外创建目录。如果写成 `-o "logs/train.%J.out"`，应先执行 `mkdir -p logs`。

参数含义可参考[香港科技大学（广州）的 UniScheduler 作业提交说明](https://docs.hpc.hkust-gz.edu.cn/docs/hpc12/slurm/job1/)，其中列出了队列、GPU 数量、CPU 核数、日志和工作目录选项；本平台的具体默认值和限制仍以当前帮助及队列配置为准。

提交成功后，终端会返回作业号。应立即记录该编号，后续的 `jjobs` 和 `jctrl` 都会使用它。

## 6. `jjobs`：查看作业

### 查看本人的作业

```bash
jjobs
```

这是最常用的查询命令，用于查看作业号、名称、状态、队列和运行节点。

### 只看排队作业

```bash
jjobs -p
```

`-p` 用于筛选仍在等待资源的作业。

### 只看运行作业

```bash
jjobs -r
```

`-r` 用于筛选正在运行的作业。

### 查看指定作业详情

```bash
JOBID=18433
jjobs -l "$JOBID"
```

`-l` 会显示更详细的提交参数、资源申请、工作目录、运行节点和状态原因。排队时间过长或作业失败时，应优先检查这里。

<img src="../images/jjobs.png" width="85%" alt="jjobs 输出示例">

### 常见状态

| 状态类别 | 含义 | 建议 |
| --- | --- | --- |
| 等待/排队 | 尚未获得资源 | 检查队列权限、GPU 类型和资源是否申请过量 |
| 运行 | 已在计算节点执行 | 查看日志，确认程序正常推进 |
| 暂停 | 被用户或系统挂起 | 查看原因，必要时使用 `jctrl resume` |
| 完成 | 正常结束 | 检查输出文件和实验结果 |
| 退出/失败 | 异常结束或被终止 | 查看 `.err` 和 `jjobs -l JOBID` |

具体状态字符串以当前调度器输出为准。

## 7. `jctrl peek`：查看未完成作业输出

### 查看当前输出

```bash
JOBID=18433
jctrl peek "$JOBID"
```

适合快速查看未完成作业的标准输出和错误输出。

### 持续跟踪输出

```bash
JOBID=18433
jctrl peek -f "$JOBID"
```

`-f` 会持续跟踪输出，效果类似 `tail -f`。按 `Ctrl+C` 只会停止本地查看，不会终止作业。

### 查看数组作业中的指定任务

```bash
JOBID=18433
TASK_ID=3
jctrl peek -t "$TASK_ID" "$JOBID"
```

只有数组作业才需要 `-t TASK_ID`。普通作业直接使用 `jctrl peek JOBID`。

## 8. `jctrl stop`：暂停作业

```bash
JOBID=18433
jctrl stop "$JOBID"
```

用于暂停未完成作业。暂停不会删除作业，但运行中的程序可能停止获得计算资源，具体行为取决于平台策略。

暂停后检查：

```bash
JOBID=18433
jjobs -l "$JOBID"
```

## 9. `jctrl resume`：恢复作业

```bash
JOBID=18433
jctrl resume "$JOBID"
```

用于恢复已经暂停的作业。恢复后作业可能继续运行，也可能重新等待资源。

<img src="../images/jctrl_resume.png" width="85%" alt="jctrl resume 示例">

## 10. `jctrl kill`：终止作业

> 这是破坏性操作。终止前应再次核对作业号，并确认检查点和输出已经保存。

```bash
JOBID=18433
jjobs -l "$JOBID"
jctrl kill "$JOBID"
```

终止后作业通常进入退出状态，不能通过 `resume` 继续。平台不存在 `jcancel` 或 `jskill` 命令，普通终止操作使用 `jctrl kill`。

## 11. `jctrl top`：前移等待作业

```bash
JOBID=18433
jctrl top "$JOBID"
```

用于将本人的等待作业移动到队列前部。它主要调整账号内部的等待顺序，不代表能够越过调度策略、管理员优先级或其他用户作业。

## 12. `jctrl bot`：后移等待作业

```bash
JOBID=18433

```

用于将本人的等待作业移动到队列后部，适合暂时降低某个等待作业的顺序，让同账号其他作业优先。

## 13. `jctrl requeue`：重新排队

> `requeue` 可能终止当前执行实例并重新排队。使用前应确认程序支持从检查点恢复，否则可能丢失本轮尚未保存的计算进度。

```bash
JOBID=18433
jjobs -l "$JOBID"
jctrl requeue "$JOBID"
```

重新排队后再次运行：

```bash
jjobs
```

检查作业是否重新进入等待状态，以及作业号和提交参数是否发生变化。

## 14. 查看已经写入文件的日志

`jctrl peek` 主要用于未完成作业。使用 `-o hello.out` 提交后，可以查看已经写入文件的输出：

```bash
cat hello.out
```

持续查看日志：

```bash
tail -f hello.out
```

按 `Ctrl+C` 退出 `tail -f` 不会影响远端作业。如果提交时使用了其他文件名，将 `hello.out` 换成对应的文件名。

## 15. 一次完整的作业流程

```bash
# 1. 查询本人可用队列
jqueues -u "$USER"

# 2. 提交一个打印计算节点名称的作业（normal 需为可用队列）
jsub -q normal -o hello.out hostname

# 3. 查看作业状态
jjobs

# 4. 作业完成后查看结果
cat hello.out
```

需要查看某个作业的详情时，运行 `jjobs -l JOBID`，将 `JOBID` 换成提交成功后返回的真实作业号。

## 16. 常见问题排查

### 作业一直排队

依次检查：

```bash
jqueues -u "$USER"
jhosts
jjobs -p

JOBID=18433
jjobs -l "$JOBID"
```

常见原因包括队列关闭、没有权限、指定 GPU 类型暂时无空闲资源、CPU/内存/GPU 申请过量，或账号达到并发上限。

### 作业提交后立即失败

```bash
JOBID=18433
jjobs -l "$JOBID"
jctrl peek "$JOBID"
```

重点检查：

- `-cwd` 指向的目录是否存在。
- Python 或可执行文件是否存在并具有执行权限。
- 日志目录是否提前创建。
- 输入文件、数据目录和配置文件是否可读。
- 作业脚本是否使用了只在交互式 Shell 中存在的环境。

### GPU 程序看不到 GPU

确认作业确实通过 GPU 队列提交并申请了 `-gpgpu`：

```bash
JOBID=18433
jjobs -l "$JOBID"
jctrl peek "$JOBID"
```

登录节点的 `nvidia-smi` 无法连接 GPU 驱动，登录节点测试不能证明计算节点 GPU 是否可用。

### 输出文件没有生成

提交前先创建目录：

```bash
mkdir -p "$HOME/logs"
test -w "$HOME/logs"
```

同时确认 `-o`、`-e` 路径正确，并使用 `%J` 区分不同作业。

## 17. 提交前检查表

- 已用 `jqueues -u "$USER"` 确认本人可用队列和 `Open:Active` 状态。
- 已用 `jhosts` 确认所需节点资源和 GPU 类型当前存在。
- 如果日志路径包含子目录，已提前创建该目录。
- `-cwd`、Python、脚本、配置和数据路径都正确。
- CPU、内存、运行时限和 GPU 申请与程序规模相符。
- 已通过 `-o` 指定输出文件；重复提交时可用 `%J` 区分日志。
- 训练、编译和 GPU 测试没有直接在登录节点运行。
- 已记录作业号，并准备通过 `jjobs -l` 和日志检查运行状态。
